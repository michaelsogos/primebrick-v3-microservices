# JobHandler (`primebrick-job`)

JobHandler is the **scheduler, governance, and observability** service for the
Primebrick job fabric. It never executes domain work — every job's executor
lives in the owning domain service.

## Architecture

```
job_triggers row            triggers engine                JetStream           owning service
────────────────            ────────────────               ─────────           ──────────────
user-made (entity API)  or
module-declared via ──▶ engine derives + arms ──▶ jobs.schedule.job.<trigger-uuid>
jobs.ctl.triggers.materialize                          (atomic protocol)        │ (NATS native scheduler)
                                                                                ▼
                                                                   jobs.due.<lane>.job.forward.<uuid>
                                                                                │ forwarder resolves
                                                                                ▼ actor + payload_map
                                                                   callable subject ──────────────▶ executor
                               ◀── jobs.result.<svc>.<name> ◀── durable consumer  (route handler)
                               │
                               ▼
                         job.job_runs (status, duration, error, report)
```

- **Scheduler** = the NATS server (`allow_msg_schedules` on the `JOBS` stream).
- **Sole writer of `jobs.schedule.*`** = job-handler's triggers engine —
  every schedule mirror is owned by a `job_triggers` row (`trigger_uuid`,
  NOT NULL). There is no external arm route: modules declare jobs through
  `jobs.ctl.triggers.materialize` (system triggers, `system_key`-anchored),
  users through the canonical entity API; the engine derives and arms the
  schedule itself.
  Arm/disarm is an **atomic protocol**: declare → PubAck → read-back
  verify → mirror upsert (a mirror failure compensates with a purge);
  disarm verifies the declaration is *absent* before flipping the mirror.
  Re-arming an already-fired/expired `@at` for the same spec is a
  successful no-op (`skipped: "terminal-once"` — a past `@at` would fire
  immediately on re-declare).
- **Spec grammar** = `"@every <int><s|m|h|d>"`, `"@at <ISO-8601>"` one-shots,
  5-field cron `m h dom mon dow` (UTC). Recurring specs floor at **one
  minute** — `@every 30s` is rejected at every layer (field validation
  `schedule_spec_min_interval`, the trigger shape rule
  `SCHEDULE_BELOW_MIN_INTERVAL`, and the `declareSchedule` arm backstop);
  `@at`/cron are exempt by construction (one-shot; the grammar cannot go
  below a minute).
- **Executor** = a durable JetStream consumer inside the domain service —
  for trigger targets, the `jobs.due.<lane>.job.forward.<uuid>` trampoline
  whose forwarder re-resolves the actor and republishes to the callable
  subject with fresh auth.
- **Triggers** = `job.job_triggers` domain data (NOT config) — the triggers engine
  dispatches them: event+schedule gate, event-only immediate, schedule-only timer.
  System triggers (`system_key IS NOT NULL` → `is_system`) are materialized
  by modules via `jobs.ctl.triggers.materialize` with delta-only reconcile:
  code-owned fields (`event_subject`, `target_subject`, `run_as`,
  `payload_schema`, `payload_map`, `system_key`) update on drift, user-owned
  fields (`name`, `schedule_spec`, filter) are never overwritten.
- **Infrastructure jobs** = metadata-derived declarations (`@PartitionField`
  on an entity) expressed as system triggers — e.g. AI partition
  maintenance — governed like every other trigger (users can retune the
  schedule; the code-owned contract stays frozen).

## Subjects

| Subject | Purpose |
|---------|---------|
| `jobs.schedule.<owner>.<name>` | Schedule declaration (stored, last-msg-wins) |
| `jobs.due.user.<svc>.<action>[.<id>]` | Due message — user lane (auth propagates) |
| `jobs.due.system.<svc>.<action>[.<id>]` | Due message — system lane |
| `jobs.result.<svc>.<name>` | Execution report → recorded in `job.job_runs` |
| `jobs.cancel.*` | Schedule cancellation |
| `jobs.ctl.triggers.materialize` | System-trigger materialization (service-shielded callNats route) |

## Namespace security

System triggers anchor on `system_key = <svc>.<name>` — the materialize
route refuses a `system_key` outside the caller's own service namespace
(service-shield L1+L2 verified). Schedule declarations live in the `job`
namespace (`jobs.schedule.job.<trigger-uuid>`) and the engine may target
any service's due lane — that's the point of triggers.

## Domain data (schema `job`)

- `job_triggers` — business triggers: `event_subject` and/or `schedule_spec`
  (at least one) → `target_subject`; `run_as`: `originator`|`author`|`system`
  (originator/author dispatch on the user lane, system on the system lane).
- `job_schedules` — **read-only mirror** of NATS declarations. Every row is
  owned by a `job_triggers` row (`trigger_uuid`, NOT NULL) — user-made and
  module-declared system triggers alike; the triggers engine is the only
  materialization path. Columns: `schedule_type`: `recurring` | `once`,
  `status`: `armed` | `stopped` | `paused` | `disarmed` | `fired` | `expired`.
  Lifecycle semantics: `stopped` = instance stop (temporary — the owner may
  re-arm); `paused` = suppressed re-arm until resume (`enabled` untouched);
  `disarmed` = owner-level off (the owning trigger soft-deletes — only an
  explicit enable restores it).
- `job_runs` — execution history: `status` (`dispatched` | `succeeded` | `failed` | `lost` | `skipped`),
  `duration_ms`, `fire_seq`, error fields, report (jsonb). `skipped` is the
  pause/suppression audit trail: a queued due honored while its schedule is
  no longer `armed` records a skipped run (no callable dispatch).
  `fire_seq` is the due fire's JetStream stream sequence, stamped by the
  due-forwarder at insert on every path (dispatched/skipped/failed). The
  SDK transport middleware publishes `jobs.result.<svc>.<name>` for every
  correlated handler (`x-job-run-id` / `x-job-schedule-subject` headers);
  a `dispatched` run that never gets a result is flipped to `lost` by the
  sweeper.
- `config_entries` — mandatory per-service config (cadence, ports, shield refs).
  `reconcile_interval_ms` (default `300000`, `0` disables) drives the
  periodic mirror-vs-NATS reconcile; the boot-time pass always runs.

### Mirror semantics — `job_schedules`/`job_triggers` are NOT the truth

The live schedule truth is the set of JetStream declarations on
`jobs.schedule.<svc>.<name>`; `job_schedules` (and `job_triggers`) are
**mirrors** for admin/history. Writes must go through the canonical paths
(`disarmSchedule`, trigger disable, `jobs.ctl.*`) — a direct SQL
`UPDATE status='disarmed'` leaves the NATS declaration **firing** until a
reconcile pass purges it. Boot reconcile + the periodic interval
(`reconcile_interval_ms`) converge mirror↔NATS: stale declarations are
purged, orphan declarations are purged strictly, and armed-missing rows are
re-derived via the engine's `refreshTrigger` on their owning trigger. The
list endpoint decorates
each row with `live`/`drift` (`stale` = mirror terminal but NATS still
fires — dangerous; `missing` = armed but no declaration).

## HTTP surface (via BE `/svc/job/*` proxy)

| Route | Description |
|-------|-------------|
| `GET /api/v1/entities/job_trigger|job_schedule|job_run/…` | Canonical entity CRUD (meta/list/get/…) |
| `POST /api/v1/actions/stop-job` | STOP — purge the schedule instance (temporary; owner may re-arm) |
| `POST /api/v1/actions/disable-schedule` | DISABLE — owner-level off: the owning trigger soft-deletes |
| `POST /api/v1/actions/enable-schedule` | ENABLE — owner-level re-arm: unsuppress + restore + re-derive the owning trigger |
| `POST /api/v1/actions/pause-schedule` | PAUSE — suppress every re-arm path until resume (`enabled` untouched) |
| `POST /api/v1/actions/resume-schedule` | RESUME — clear pause + re-derive the owning trigger |
| `POST /api/v1/actions/disarm-all` | DISABLE ALL (bulk) — every armed/stopped owner off |
| `POST /api/v1/actions/pause-all` | PAUSE ALL (bulk) — freeze every armed schedule |
| `POST /api/v1/actions/resume-all` | RESUME ALL (bulk) — thaw every paused schedule |
| `POST /api/v1/actions/job-run-stats` | Per-schedule execution buckets for sparklines — adaptive `bucket_unit` (hour/day/week/month chosen so the span lands in ~8–30 buckets) |
| `POST /api/v1/actions/schedule-drift` | Drift diagnostic (admin, read-only): last reconcile report + live NATS enumeration and the rows currently drifting |

## Partition maintenance (first real consumer)

`@PartitionField` on an entity marks it partitioned; `@PartitionChildOf` marks
the logical children purged leaf→root before each partition drop. The owning
service calls `dal.partitionMaintenance(ENTITY_REGISTRY)` from its executor —
job-handler only sees subjects, never tables.

Config: `partition_maintenance_schedule` in the service's `config_entries`
(default `@daily`).

## Fire-time auth freshness

Every scheduled/immediate user-lane dispatch crosses the due-forwarder
(`jobs.due.user.job.forward.>`), which runs a mechanical auth checkpoint
before republishing: the actor's resolved AuthUser is cached under
`auth:snap:<uuid>` and reused only while it postdates the BE-stamped
epochs (`auth:epoch` global on role writes, `auth:user_epoch:<uuid>` on
user writes). Miss/expired/epoch-stale → re-resolve via
`auth.ctl.resolve_user`; `null` (deleted/disabled actor) → the fire is
refused and the run recorded `failed`; an unreachable backend **throws**
(`AuthCheckpointUnreachable`) — the handler naks and the fire defers to
the next redelivery, because forwarding arm-time headers would let the
callable accept stale claims (roles frozen at arm time). Unverifiable
authorization is never forwarded; both due-lane durable consumers bound
redelivery with `maxDeliver: 5`. System lane bypasses it.

## Admin UI

The job module owns its UI via `JOB_NAV` (`src/nav-declaration.ts` →
`service_registry.endpoints.nav`, `route_prefixes: ["/system/job"]`,
access namespace `access.system.job`).

- **List pages** (`kind: "list"`) — schedules / runs / triggers lists are
  host-rendered entity-table archetypes with per-row Kestra-style
  stacked-bar execution sparklines.
- **Trigger create/detail** (`kind: "create"/"detail"` + `page_props.form`)
  — the host entity-form archetype renders them; the mutually-mandatory
  source/schedule pair and the lane policy ride the closed-vocab
  `job_trigger_shape` validator.
- **Remote sheet** (`nav.sheets[]`) — `job.runDetail` mounts the run
  drill-down panel from the same chunk via the host sheet engine.
- **Serving**: `GET /api/v1/module-assets/*` streams `fe/dist` (vite build
  under `fe/`); the gateway path is
  `/svc/job/api/v1/module-assets/jobs-page.js`.
