# CRM (`primebrick-crm`)

CRM is a **playground/case-study service** for the module-ownership
architecture — not a business product module. It proves that a microservice
can own its own navigation, route prefixes, translations, entity APIs and
remote pages through service registration. It will eventually be split out
into a standalone product.

## What it does today

- Declares the `crm` **root level** (`partOf: "crm"` — the CRM module IS its
  own root level, unlike the `system` services).
- Owns the `/crm` route prefix: `/crm/customers`, plus an extra root-level
  membership under `system` (`/system/crm/pipeline` — "a foot in two shoes").
- Registers `CRM_NAV` (`nav-declaration.ts`) via `service_registry.endpoints.nav`.
- Translates its own module label (`labelKey: "crm.module.name"`) in the
  `crm.translations` namespace.
- **Owns the `customer` domain entity end-to-end** — entity class
  (`domain/entities/customer_entity.ts` → `crm.customers` + `crm.customers_audit`),
  `CustomersService extends DomainService`, meta, list config, zod schemas,
  `crm.entities.customer.*` translations (`entities_ns: "crm"`), and the
  meta-derived export pipeline (`templates/customer_export_template.*`).

## HTTP surface

- `src/controllers/http/entities-route.ts` — `EntityRouteDecl[]` for
  `customer`: `/api/v1/entities/customer/meta|list|export|duplicate|
  bulk-delete|bulk-restore|:uuid[/audit|/restore]` (no `purge` — customer
  never declared it). Permission literals stay `Permission.CUSTOMER_*`.
- `src/controllers/http/composite-route.ts` — `makeServiceRoutes` derives
  BOTH the CRUD routers and `/api/v1/openapi.json` from ONE declaration;
  the spec can never drift from registered routes.
- `src/controllers/http/module-assets-route.ts` — serves `fe/dist` remote
  page chunks at `GET /api/v1/module-assets/*` (the `component_url` the
  nav declarations point at). Reached via the BE proxy as
  `/svc/crm/api/v1/module-assets/...`.
- MCP reaches `customer` as `module=crm`, `handler_type: "proxy"` — the
  OpenAPI-driven entity discovery auto-registers it on service enrollment.

## Remote pages

`fe/` is a vite+svelte remote-chunk build (`fe:build` → `dist/crm-pages.js`):
`/crm/customers/create` and `/system/crm/pipeline` are module-owned remote
pages (`component_format: "esm-mount"`), mounted by the FE catch-all through
`RemotePageMount`. The list page stays host-rendered (`kind: "list"`).
`bindRemoteCtx(ctx, { service: 'crm' })` wires service-scoped i18n/API.

## Boundaries

- **No NATS subscribers** — HTTP surface only (entity CRUD + openapi +
  module assets).
- **DB ownership**: owns its own `db-meta/` (signed `MANIFEST.json`,
  `keys.json`, `patches/` — `0005_customers_ownership.sql` moved
  `customers`/`customers_audit` from `public` into `crm`).
- **Root level `crm`** is distinct from `system`: `service_registry.part_of`
  separates the two domains (see `overview.mdx`).

## Configuration

- Port: **3007** (`config_entries.http_port`, seeded by `0002_seed_config.sql`).
- Env policy: `DATABASE_URL` + `DATABASE_SCHEMA` only (see
  `docs/ai/env-policy.md`); everything else lives in `config_entries`.
- Dev: `bun --hot src/index.ts` from `primebrick-us-v3/crm/`.
- Docs pack: `pnpm generate:docs` → `dist/docs-pack` (openapi-only pack).

## Adapters

- `ConfigRepositoryAdapter` — `config_entries` governance.
- `HealthCheckAdapter`, `CrmAuthConfigPort` — SDK lifecycle ports.
